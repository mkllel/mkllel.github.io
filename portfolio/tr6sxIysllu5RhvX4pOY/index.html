인프라 · 운영

복구 검증 기반 자동 백업 시스템

Proxmox 홈랩의 파일, 데이터베이스, 가상머신을 보호하는 운영 자동화 Proxmox 홈랩의 파일, DB, VM/LXC를 자동 백업하고 유형별로 무결성과 복구 가능성을 검증하는 시스템을 구축했습니다. 정기 백업, 무결성 검사, 격리 환경의 복원 검증, 보존 정책, VM/LXC 백업을 하나의 운영 흐름으로 연결했습니다. 정상 동작뿐 아니라 실행하지 말아야 할 조건과 실패 이후의 복구 과정도 함께 설계했습니다.

담당
백업 정책과 실행 흐름 설계, 검증 로직 구현, 운영 대시보드, 안전장치 및 복구 절차 구성
기술
Python · restic · Proxmox vzdump · systemd · PostgreSQL · SQLite
결과
정기 백업 6개 무인 실행 및 복원 검증, VM·LXC 아카이브 5개 검증, 별도 VM에서 암호화 백업 복호화 및 복원 확인
01

문제 — 백업 파일이 있다는 것만으로 충분한가?

여러 서비스를 상시 운영하면서 가장 우려했던 것은 장애 자체보다 복구할 수 있는 데이터가 남아 있는지였습니다.

백업 작업이 성공해도 파일이 손상됐거나 데이터베이스를 열 수 없다면 복구에 사용할 수 없습니다. 백업 서버에 의존해야만 복호화할 수 있는 구조 역시 장애 상황에서는 복구를 어렵게 할 수 있습니다.

그래서 완료 기준을 ‘백업 생성 성공’과 ‘복구 검증 완료’로 나눴습니다. 각 단계의 결과와 실패 지점을 추적하고 운영 원본을 건드리지 않는 임시 공간에서 복원된 데이터를 확인하도록 설계했습니다.

기존 홈랩 프로젝트가 실행 환경과 서비스 격리에 초점을 맞췄다면, 이 프로젝트는 그 환경의 데이터를 어떻게 보호하고 복구 가능성을 확인할 것인지에 집중했습니다.

02

설계 — 백업과 복원 검증을 하나의 흐름으로 연결

백업 애플리케이션은 별도의 비특권 LXC 컨테이너에서 운영하고 외장 HDD의 전용 영역을 저장소로 사용했습니다.

파일과 데이터베이스는 유형별로 백업하며 가상머신과 컨테이너는 Proxmox의 native backup으로 별도 보호했습니다.

파일과 DB 백업의 실행 및 검증 흐름은 다음과 같습니다. VM과 LXC는 별도의 native backup 경로에서 아카이브를 검증합니다.

정기 정책 실행
→ 저장소·실행 충돌 검사
→ 백업 생성
→ 무결성 검사
→ 격리된 임시 공간에 복원
→ 파일·DB 검증
→ 결과 기록 및 대시보드 표시

파일 백업 3개와 데이터베이스 백업 3개를 매일 순차적으로 실행합니다. PostgreSQL은 논리 백업을 사용합니다. SQLite는 복원된 DB의 integrity_check 결과와 스키마, 주요 테이블, 대표 조회를 확인합니다.

실제 정책 실행 기록과 새 아티팩트, 무결성 검사, 복원 검증 결과가 연결되는지 확인하도록 구성했습니다.

03

문제 해결 — 백업이 운영 장애를 만들지 않도록

SSHFS/FUSE를 사용하는 컨테이너의 백업 방식 분리

백업 전용 LXC 컨테이너 CT200은 내부에서 SSHFS/FUSE로 저장소에 접근하고 있었습니다. 이 상태에서 컨테이너를 freeze하는 snapshot 백업을 적용하면 FUSE와 교착이 발생할 위험이 있었습니다.

저장소를 백업 대상에서 제외하는 것만으로는 이 실행 구조의 위험을 없앨 수 없었습니다.

따라서 CT200만 정상 종료 후 백업하는 stop 모드로 분리했습니다. 나머지 게스트는 snapshot 모드를 유지했고 외부 저장소의 실제 데이터가 컨테이너 아카이브에 중복 포함되지 않는지도 확인했습니다.

자동 stop 백업 전에는 다음 상태를 검사하도록 구성했습니다.

  • 실행 중인 백업 작업
  • 대기 중인 작업
  • 애플리케이션 작업 잠금
  • restic 저장소 잠금

작업이나 잠금이 확인되는 busy 상태에서는 기존 작업을 강제로 중단하지 않고 SKIPPED로 기록한 뒤 exit 0으로 종료합니다. 실제 저장소나 설정 오류는 정상적인 건너뛰기와 구분해 ERROR로 기록합니다.

재기동 이후 저장소 자동 연결 실패 해결

stop 모드 검증 과정에서는 컨테이너가 다시 시작된 뒤 SSHFS가 자동 연결되지 않는 문제가 드러났습니다.

기존 network-online 의존성만으로는 실제 인터페이스가 준비될 때까지 기다리지 못했습니다. 네트워크 준비가 끝나기 전에 SSHFS 연결을 시도하면서 Connection reset by peer가 발생했습니다.

wait-online 의존성을 반영해 실제 인터페이스 준비를 기다리도록 수정하고 다음 시작 순서를 맞췄습니다.

네트워크 준비
→ SSHFS 연결
→ 백업 저장소 확인
→ 백업 애플리케이션 시작

이후 수동으로 mount하거나 애플리케이션을 시작하지 않아도 저장소와 서비스가 자동 복구되는 것을 확인했습니다.

04

안전장치와 보존 정책

저장소가 연결되지 않은 상태에서 시스템 디스크에 백업이 쌓이는 일을 막기 위해 mount, 파일시스템, UUID, 전용 marker와 여유 공간을 검사합니다.

조건이 확인되지 않으면 작업을 진행하지 않는 fail-closed 방식을 적용했습니다. 최소 여유 공간 기준은 250GB로 두었습니다.

보존 정책은 파일과 DB를 구분해 적용했습니다.

대상일간주간월간연간
파일 백업3012123
DB 백업14863

자동 정리 시에는 최신 정상 스냅샷, 최신 검증 완료 스냅샷, 유일한 스냅샷을 보호하도록 구성했습니다.

같은 HDD의 개인 파일 영역은 백업 시스템의 작업 범위에서 제외했습니다. 미디어 서비스에도 원본을 읽기 전용으로 제공하고 외부 데이터가 VM과 LXC 백업에 중복 포함되지 않도록 구분했습니다.

VM과 LXC 아카이브에는 zstd 무결성 검사, VMA 또는 TAR 구조 검사, 게스트 설정 확인과 SHA-256 검증을 적용했습니다.

백업 서버 의존성도 별도로 확인했습니다. 백업 전용 컨테이너를 이용하지 않고 다른 VM에서 실제 암호화된 SQLite 백업을 복호화하고 추출했습니다. 이어서 SHA-256, integrity_check, 조회 결과를 검증했습니다.

06

검증한 범위와 남은 한계

파일과 DB의 실제 복원 검증(Restore Verification)과 VM/LXC 아카이브 검사는 검증 수준이 다릅니다. VM/LXC는 아카이브의 무결성, 구조, 게스트 설정을 확인했으며, 실제 복원 후 부팅과 서비스 동작은 검증하지 않았습니다.

별도 VM에서 특정 암호화 백업의 독립 복구 경로는 확인했습니다. 다만 동일 물리 호스트와 저장소를 함께 잃는 전체 재해 복구 훈련(DR Drill)은 아직 수행하지 않았습니다. 다음 항목은 후속 검증 과제로 남겼습니다.

  • 전체 호스트 장애를 가정한 격리 복구 훈련
  • 복원된 VM과 LXC의 부팅 및 서비스 검증
  • 실제 복구 시간 측정
07

이 프로젝트에서 배운 점

자동화에서는 정상 경로를 실행하는 것보다 운영 상황에 맞춰 작업을 진행하거나 멈출 기준을 정하는 일이 더 어려웠습니다.

작업 중인 서비스를 백업 때문에 강제로 멈추지 않고 저장소가 불명확하면 기록을 시작하지 않도록 했습니다. 검증된 사본을 정리 과정에서 보호하는 일도 백업 기능의 일부였습니다.

이 프로젝트를 통해 성공 로그뿐 아니라 실제 검증 결과와 남은 한계까지 근거로 남기는 방식으로 운영 자동화를 설계했습니다.

백업의 완료 기준은 파일이 만들어졌다는 사실이 아니라, 검증한 범위 안에서 다시 사용할 수 있다는 증거입니다.
